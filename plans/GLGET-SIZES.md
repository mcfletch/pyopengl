# glGet output sizes are a memory-safety boundary

**Status:** Landed. `GL_PATCH_DEFAULT_INNER_LEVEL` and
`GL_PATCH_DEFAULT_OUTER_LEVEL` were recorded one value each; the driver writes
two and four. `tests/gl/test_glget_sizes.py` now walks the whole shipped table
against the live driver so a recorded size cannot go short again.

## What a wrong size costs

`glGetFloatv(pname)` allocates its output array from the recorded size and hands
the driver a pointer. Where the record is smaller than what the driver writes,
the driver writes past the end of a live allocation. Nothing raises: the bytes
belong to some other object, and the program continues with that object
quietly damaged. On Windows the NT heap notices at the next free and the
process dies with `0xC0000374` (`STATUS_HEAP_CORRUPTION`) somewhere unrelated —
in this case inside `glfw.destroy_window`, one test later, in a run whose tests
had all passed.

Detection is the part that misleads. The overrun is the same on every run; what
varies is whether later allocation traffic happens to make the heap validate
the block that was hit. Bisecting on "does it crash" therefore measures
allocation patterns, not the defect: deselecting any of five unrelated tests
made the crash disappear, and running those five together was clean. The
sentinel probe below answers the actual question and does it in one pass.

## Where the sizes live

Three copies, all generated from one source, and all three must be regenerated:

| File | Generated by |
| --- | --- |
| `src/glgetsizes.csv` | hand-maintained; the source of truth |
| `OpenGL/raw/*/_glgets.py` | `python src/regen_glgets.py` |
| `accelerate/src/c/generated/pygl_glgets.h` | `python src/regenerate_c.py` |

The ctypes path reads `_glgets.py`; the C dispatch path compiles the header into
`OpenGL_accelerate.dispatch`. Correcting the CSV and regenerating only the
Python leaves the C path still overrunning, which is what it did here until the
extension was rebuilt.

**A regenerated header does not rebuild the extension on its own.**
`setup.py build_ext` compares timestamps and reported success without
recompiling anything, leaving a stale `dispatch.pyd` that still held the old
sizes — with the Python side already correct, so the two paths disagreed.
`build_ext --force` is what actually rebuilds it. Check the built module rather
than the exit status:

    PYOPENGL_DISPATCH=c python -c "from OpenGL.GL import glGetFloatv; print(glGetFloatv(0x8E74))"

## Measuring what the driver writes

Fill an oversized buffer with a sentinel, call the *raw* entry point (never the
wrapper, whose allocation is the thing under suspicion), and count the slots
that changed. Two different sentinels, so a slot the driver legitimately sets
to the sentinel value is not read as untouched.

`tests/glget_check.py` holds the implementation, `tests/glget_audit.py` runs it
over the pnames named in `tests/gl/glget_groups.json`, and
`tests/gl/test_glget_sizes.py` runs it over every key in the shipped table.
The audit missed these two because no group lists them — the table is the wider
set, and the table is what allocates.

Only under-allocation is a defect. Recording more than the driver writes wastes
a few bytes on the stack of a call, and the audit reports it separately.
