The C dispatch layer

PyOpenGL has two implementations of the OpenGL entry points. The ctypes implementation is the one it has always had and is the default. The C implementation is generated from the Khronos registry, compiled into an extension module, and selected with an environment variable:

PYOPENGL_DISPATCH=c   python yourprogram.py

Both implement the same API. A call reaches the driver about seven times faster through the C implementation, and about eleven times faster for a call that passes an array; the numbers below are on a GeForce RTX 3060 Ti with CPython 3.12 and OpenGL_accelerate installed.

callctypesC
glBindTexture(GL_TEXTURE_2D, 0)407 ns58 ns
glUniform1f(loc, 1.0)382 ns51 ns
glUniformMatrix4fv(loc, 1, False, m)1184 ns106 ns
an empty Python function, for scale32 ns

Selecting an implementation

PYOPENGL_DISPATCH=ctypes
The default. It is the reference semantics, the bootstrap route for a new platform, and what runs where no compiled wheel is available. It is not scheduled for removal.
PYOPENGL_DISPATCH=c
Use the C implementation for every entry point that has one. An entry point it does not implement keeps its ctypes binding, so the two coexist and you never have to choose per function.

Installing from source without a compiler is supported: the extension is optional, and its absence leaves the ctypes implementation in place.

What is implemented in C

4,560 of PyOpenGL's 4,839 bindings, across GL, GLES 1/2/3, GLSC2, GLX, WGL and EGL. The rest keep their ctypes binding, and python src/check_registry.py lists them with the reason for each. The families still on ctypes are the ones whose behaviour is a computation rather than a description: images, whose size depends on format, type, dimensions and the current pixel-store state; the variadic entry points such as glVertex and glColor; the client-side array pointer family; and glShaderSource.

Contexts

Under the C implementation each OpenGL context holds its own function pointer for every entry point, resolved in that context. This matters where two contexts differ: a discrete-GPU context beside a software one, a core context beside a compatibility one, or GLES beside desktop GL. Under the ctypes implementation whichever context resolved an entry point first determines the binding for the whole process.

Two consequences reach the Python surface. bool(glFoo) and glInitXxx() answer for the context that is current, so the same expression can correctly be true in one context and false in another. And a binding held in a local variable across a context switch still dispatches correctly, because the entry point object holds a slot index rather than an address.

Telling the layer that the context changed

PyOpenGL does not see your windowing toolkit call MakeCurrent, and asking the driver which context is current costs about 95 ns — more than a whole dispatch — so it is not asked on every call. Instead:

  • A process with one context needs to do nothing.
  • When an entry point is used for the first time in a context, the layer re-reads the current context, so a new context picks up its own pointers for everything it has not called yet.
  • An application that switches between contexts and wants that to be exact calls OpenGL._dispatch.make_current(handle) after each switch, with the handle OpenGL.platform.PLATFORM.GetCurrentContext() returns.
  • PYOPENGL_CONTEXT_TRACKING=strict asks the driver on every call instead. It is exact and it costs the 95 ns; it exists for diagnosing a multi-context program, not for shipping.

OpenGL._dispatch.forget_context(handle) releases a destroyed context's table. A table is about 32 KB, so a hundred live contexts cost 3 MB.

Arrays

Nothing you can pass today stops being accepted. Where an array is wanted, a buffer whose element type already matches is used directly; anything else — a different dtype, a non-contiguous array, a list, bytes, a ctypes object, a VBO, an object from a FormatHandler you registered yourself — is converted by ArrayDatatype exactly as it is today. A type the C layer does not recognise is not an error; it is simply not accelerated.

Registering a new array type therefore needs no knowledge of this layer, and a type registered against an older PyOpenGL keeps working. Acceleration is optional; acceptance is not.

Error checking

OpenGL.ERROR_CHECKING is read when the layer is configured and applies per entry point per context. glGetError is called from C rather than through a Python callback, so checking costs the driver round trip and nothing else. OpenGL._dispatch.set_error_checking(enable, entry_point=None) changes it at run time, for one entry point or for all — which the import-time flag cannot do.

Checking through GL_KHR_debug

The round trip is the cost of error checking. Where the context offers GL_KHR_debug, the driver can report an error through a callback during the call instead, and the check afterwards becomes a read of the flag that callback set:

import OpenGL._dispatch as dispatch
dispatch.use_debug_output(True)
glBindTexturens
checking via glGetError48.9
checking via GL_KHR_debug38.4
no checking at all37.6

Checking costs 0.8 ns rather than 11 ns, so leaving it on is no longer a trade against speed. The exception is the same GLError, raised from the same call; the description is the driver's own message rather than a code looked up afterwards.

It requires a context with GL_KHR_debug; use_debug_output() returns False and leaves checking as it was where there is none. It turns on GL_DEBUG_OUTPUT_SYNCHRONOUS, because the callback has to run during the call it belongs to for the error to be attributed to the right entry point. Messages that are not errors are not requested, so the driver does not spend time formatting them.

Docstrings and introspection

Entry points carry a docstring and a text signature under the C implementation, which they do not have under ctypes:

>>> glBindTexture.__doc__
'glBindTexture(target, texture) -> None'
>>> glGenTextures.__doc__
'glGenTextures(n) -> textures'
>>> inspect.signature(glGenTextures)
<Signature (n, textures=None, /)>

The signature is built from the registry, so it is available for every entry point without any external documentation source.

What differs from the ctypes implementation

These are the differences a program can observe. Everything not listed here behaves identically, and the test suite runs under both implementations to keep it that way.

behaviourctypesC
type(glBindTexture) a ctypes function pointer, or _NullFunctionPointer GLProc. An isinstance check against ctypes._CFuncPtr is the one idiom likely to notice.
repr(glBindTexture) ctypes' wording <OpenGL entry point glBindTexture>
exception message text for a bad argument ctypes' wording ours. The exception type is preserved: ctypes.ArgumentError for a bad argument, NullFunctionError for an absent entry point.
bool(glFoo), glInitXxx() resolved once, cached for the process answered for the current context
a call with no current context undefined unless CONTEXT_CHECKING is on, which it is not by default raises OpenGL.error.NoContext. The check became free, so it is always on.
OpenGL.FULL_LOGGING logs every call not implemented in C. Tracing selects the ctypes implementation for the process.

Ways out

Assigning errcheck or argtypes to an entry point moves that one entry point to the ctypes implementation for the life of the process, so a debugging habit that relies on either keeps working. Assigning restype the conversion the entry point already performs changes nothing; assigning a different one moves it likewise. PYOPENGL_DISPATCH=ctypes is the way out for everything else.

Regenerating and keeping up with the registry

python src/regenerate_c.py     # registry and shipped tree in, C out
python src/check_registry.py   # what changed, and what needs a person

check_registry.py reports registry commands with no binding, bindings whose signature no longer matches, enums with no constant, and every entry point still on the ctypes path with the reason. Differences that are already known are recorded in src/cdispatch/registry_baseline.json with a reason for each, and the tool exits non-zero only for what is new since, so it can drive a scheduled job.
